1. Цель и отличие от Day 11

Memory: «Что агент знает / помнит?» Personalization: «Как агент должен работать с этим пользователем?» Личная память о краткости становится структурированным detail_level=brief; Context Builder применяет настройку до генерации.

Ниже сохранены настоящие ответы одной модели, без ручной правки и без второго LLM-переписывания. Табличный Markdown показан дословно для проверяемости.

2. Архитектура UserProfile

USER → USER PROFILE (style / format / detail / constraints)
CURRENT MESSAGE ───┐
SHORT-TERM ────────┤
WORKING MEMORY ────┤
LONG-TERM MEMORY ──┼→ CONTEXT BUILDER → LLM → PERSONALIZED RESPONSE
DOMAIN DATA ───────┤
USER PROFILE ─────┘

User остаётся identity. UserProfile — типизированный вид существующего user_preferences.settings_json, ключ user_id. Отдельной таблицы или конкурирующей копии профиля нет. Audit Log хранит provenance и trace.

3. Поля и значения по умолчанию

style=neutral; detail=normal; language=ru; format=text; summary_first=false; confirmation=confirm_destructive; hide_llm_details=false. Подтверждения BOM и производства обязательны. Язык en можно хранить, но текущая генерация/UI работают на русском.

4. Подключение к запросам

AgentContextBuilder добавляет компактный [USER PROFILE] перед генерацией; обычный интерпретатор и Telegram semantic pipeline получают тот же блок. Отчёты читают SQLite и делают один Complete-вызов. Локальные формы не обращаются к LLM. Все профили разрешаются заново по внутреннему user_id.

7. Один запрос — разные ответы

A/B выполнено с одинаковыми user/session, входным запросом и доменным snapshot, без накопления истории между вызовами; меняется только профиль. Изоляция второго пользователя проверяется отдельно. Факты: Гипс 10 кг / минимум 2 кг; Кисточки 400 шт / минимум 50; Коробки 100 шт / минимум 20.

StocksPresent — только автоматическая проверка наличия названий/чисел, не доказательство полной семантической точности ответа. Тексты доступны для ручной проверки ниже.

8–10. Автоматическое применение и изменения

Новая сессия получает сохранённый профиль без напоминания. «В этот раз объясни подробно» меняет только effective detail для текущего запроса. Следующий запрос возвращается к brief. «Теперь всегда отвечай подробно» записывает настройку; новая сессия сохраняет detailed.

12. Авторизация и приоритеты

Security / authorization / business rules > явный текущий запрос > требования задачи > профиль > личная память > defaults. Preferences не выдают permissions и не отменяют обязательные кнопки подтверждения. Эти границы проверяются интеграционными тестами с тестовым транспортом; live-запросы ничего не изменяют в домене.

13. Вывод и ограничения

Персонализация подключена до генерации, сохраняется между сессиями и мастерскими. В отчёте можно сравнить фактические различия оформления. Token overhead — оценка UTF-8 bytes / 3, usage — данные провайдера. Естественные команды настроек ограничены явными поддержанными фразами. Настройки не меняют обязательный UX складских форм.
