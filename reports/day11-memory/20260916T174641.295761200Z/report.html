01. Цель и результат

Дать агенту явную модель памяти: разговор, состояние текущей задачи и устойчивые знания хранятся отдельно, выбираются по scope и не подменяют склад или BOM. Этот отчёт содержит реальные ответы одной настроенной LLM в четырёх условиях. Данные эксперимента синтетические; рабочая база не использовалась.

Short-Term

Текущий диалог, ссылки и уточнения.

user + workshop + session

Working

Количество партии, выбранный продукт, временные параметры.

user + workshop + task

Long-Term

Личные предпочтения и подтверждённые общие правила.

user / workshop / product / process

04. Контролируемое сравнение A–D

A: без memory. B: Short-Term. C: Short-Term + Working. D: все три слоя. Identity, текущий вопрос, snapshot Domain DB, модель и настройки одинаковы внутри каждого сценария. Каждый вызов начинается с нового HTTP-запроса без скрытой истории провайдера.

Шесть сценариев × четыре варианта = 24 вызова. Здесь проверяется генерация ответа через тот же LLM-клиент; рабочий агент сохраняет роль LLM-интерпретатора и выдаёт складские/BOM-результаты детерминированным кодом. Его многошаговые диалоги отдельно покрыты integration tests.

Один прогон, без статистической оценки. «Проверка» означает наличие ожидаемого факта или формата; уточнения и неверные предположения определяются узкими эвристиками. Это наблюдения, а не универсальная оценка качества модели.

06. Изоляция, права и надёжность

Memory retrieval проверяет текущую мастерскую и активную Membership. Personal records доступны только владельцу User; shared records ограничены workshop_id, product records дополнительно entity_id. Рабочая задача и сообщения проверяют собственный task/session scope. Постоянные общие знания требуют workshop.settings.manage. Изменение BOM требует bom.write; память не предоставляет обхода прав.

Persistent writes явные и подтверждаются пользователем. Изменения версионируются и записываются в существующий Audit Log. Inventory/BOM всегда остаются источником истины; старое упоминание 10 кг в сценарии 05 специально импортировано как тест устаревших данных. Обычный memory API такую складскую запись отклоняет.

Unit/integration tests проверяют отдельное хранение, lifecycle, retention, scopes, отсутствие автоматического long-term promotion, релевантный retrieval, provenance, актуальные остатки, изменение BOM и отказ EMPLOYEE без bom.write.

07. Token usage

Input/output/total usage получены из ответа провайдера для каждого вызова. Токены отдельных слоёв — локальная оценка ceil(UTF-8 bytes / 3), а не результат tokenizer модели. System-инструкции, заголовки и форматирование входят в TOTAL_PROMPT_ESTIMATE; суммы оценок нельзя приравнивать к provider usage.

Short-Term ограничена последними сообщениями и бюджетом; Working содержит одну активную задачу; Long-Term выбирается SQL-фильтрами scope/category/entity/key с LIMIT 8 плюс поддерживаемые личные preferences. В prompt не отправляется вся база памяти.

08. Вывод

История помогает с разговорной ссылкой, Working удерживает количество и временные параметры, Long-Term переносит предпочтения и правила между сессиями. Их эффект показан в ответах A–D выше, включая случаи, где модель справилась без дополнительного слоя или не выполнила ожидаемый формат. Доменные факты проверяются независимо от памяти.
