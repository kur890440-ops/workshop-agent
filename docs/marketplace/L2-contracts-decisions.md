область доступа, серверная конфигурация и общие cooldown. Определения находятся

Решения ниже нормативны; код и тесты первого этапа добавлены. Проверки — в L3.

## WA-D144 — обновление остатков при открытии в Telegram

2026-09-23, явное уточнение пользователя: «Остатки WB» и `/wb stocks` (смещение 0)
запускают `Start(scope, "wb_stocks")`. Это загрузка по действию пользователя,
не периодический опрос. Ответ о старте немедленный; после завершения отправляется
отдельное сообщение с состоянием и снимком. Ошибка не обозначается успехом.
Повторное действие при активной загрузке возвращает существующий ErrBusy.
Страницы со смещением >0 читают снимок без повторного сетевого обновления.
Склады продавца автоматически не обновляются этим действием; используется прежний
`Обновить WB` / `seller_stocks`. Перед поздним ответом повторно проверяются права,
активная мастерская и включённое подключение; текущая форма не переключается.
Уточняет прежнее описание snapshot-only `/wb stocks` и отсутствия уведомлений.
Agent/LLM и MCP не получают дополнительных полномочий. Миграций нет.

## WA-D145 — identity cache (заменяет проверку перед каждым sync из WA-D140)

Примечание: политика неизвестного профиля в WA-D146 заменена WA-D148 ниже;
правила identity остаются действующими.

Подтверждённая identity хранится только в Service в памяти 24 часа: клиент
неизменяем на протяжении жизни сервиса, ключ содержит connection/workshop/revision
и seller_id. Это срок доверия при неизменных credentials, не квота WB и не давность
остатков. Рестарт/новый клиент/смена revision/ошибка явной проверки инвалидируют
кеш. Новый токен не наследует доверие SQLite. Права и active workshop проверяются
при каждом действии и перед сетевым вызовом независимо от кеша. Явный check
всегда пытается проверить identity, соблюдая cooldown. Jobs остаются single-flight.

## WA-D146 — квоты и безопасные сроки повтора

429 не повторяется немедленно внутри job: структурированная RateLimitError
сохраняет группу операции, UTC RetryAt и источник, Unwrap возвращает RateLimited.
Используем максимум валидных Retry-After и X-Ratelimit-Retry и локального ограничения.
Reset применяется как запасной срок только при отсутствии валидных retry headers:
это восстановление burst, не обязательное ожидание при известном Retry.
Пустые/отрицательные/переполненные значения игнорируются; ноль получает минимум 1 с.
SQLite migration 111 хранит безопасный cooldown по фиксированным группам одного
источника credentials; смена токена/мастерской не сокращает известное ожидание.
Identity и токен/отпечаток не сохраняются в этой таблице. Это не распределённый limiter.
Локальное ожидание до 30 с допускается с cancellation; более длинное возвращается
сразу как локальная оценка cooldown. WB_API_PROFILE=personal/service выбирает
документированные интервалы common=1 мин, analytics=20 с. При неизвестном профиле
консервативная политика приложения common=24 ч, analytics=30 мин; эти значения
не объявляются подтверждённой квотой пользователя. Остальные лимиты без изменений.

## WA-D147 — причина сбоя и результат запроса

Ошибка identity помечает зависимую загрузку blocked_by=check, а не выдаётся за
HTTP-ответ WBStocks. Sync хранит операцию, срок/источник повтора и начало/конец
попытки отдельно от last_success. Старый снимок остаётся при ошибке. Повтор в
период cooldown получает сохранённый срок без нового HTTP. Политика WA-D144
и проверки перед поздней отправкой сохраняются. D1/V1 не закрыты mock-тестами.

## WA-D148 — снятие искусственной блокировки по запросу пользователя

Заменяет неизвестный профиль 24ч/30мин из WA-D146: common=1мин, analytics=20сек
без обязательного WB_API_PROFILE. Это локальное pacing, фактические ограничения
WB всегда учитываются; тип токена не объявляется установленным. Migration 112
однократно удаляет сохранённые local_interval и их сроки из sync-представления,
сохраняя wb_retry/wb_reset/local_backoff. Старый код мог потерять источник WB
при объединении срока с более длинным local_interval: восстановить исходный
заголовок по этой записи невозможно. Пользователь разрешил снять локальную
блокировку и сделать осторожную попытку; новый 429 прекращает запрос без ретраев.
В новом коде объединённый срок с WB header сохраняет wb_retry/wb_reset источник.
Рестарты после migration 112 не обнуляют новые ограничения. Проверка identity,
права и HTTP-защита сохраняются. Сборки: bin/workshop-agent-check.exe,
основной bin/workshop-agent.exe заменяется только после остановки.

## WA-D127 — область доступа

Каждая операция проверяет внутренние user_id, workshop_id и принадлежность
connection_id мастерской. Недоступность подключения не раскрывает данные чужого
кабинета. Права проверяются в сервисе, а не только на кнопке. Основание:
WA-D016/WA-D017 и существующий `internal/auth/service.go:Require`.
Кеш, sync checkpoint и повторный callback также ограничиваются этим scope.

## WA-D128 — подключение и permissions

В первом этапе один источник WB_API_TOKEN может быть привязан только к одной
мастерской. Первичная привязка — явное действие OWNER, не автоматическая по env.
Повторная привязка не создаёт дубликат; перенос в другую мастерскую не выполняется
неявно. Ввести раздельные permissions чтения и управления. Предлагаемая политика
для реализации: чтение активным участникам с read permission, управление OWNER;
расширение управления другим ролям — отдельное решение.
При отключении блокировать новые исходящие запросы, отменить активную загрузку
и исключить публикацию запоздалого результата. Уже отправленный запрос нельзя
«отозвать» обещанием. Переименование кабинета не является проверкой seller identity.

## WA-D129 — секрет

Секретный материал и места хранения определены [L1](L1-architecture-data.md).
Токен читается при запуске; замена требует перезапуска. `.env` содержит plaintext:
нужны ограниченные OS-права, исключение из Git и контроль backup. В `.env.example`
только пустой шаблон. Telegram показывает статус, не секрет. Ошибки и аудит
используют безопасные поля, без str(raw exception)/request dumps.
Отсутствие или неверный формат токена не должно ломать функции цеха.

## WA-D130 — публичный контракт сервиса

Смысловые операции: ConnectionStatus, AttachConnection, CheckConnection,
DisableConnection, SyncCatalog, SyncStocks, SyncOrders, ListOrders, ListStocks,
SetProductMapping. Это проектные имена, не уже существующий Go API.
Входы: context, actor/scope, типизированные фильтры/ID. Выходы: DTO без секретов,
источник и freshness/completeness, либо структурированная безопасная ошибка.
Разрешённые действия WB ограничены L0; произвольного ExecuteURL/CallAnyTool нет.

## WA-D131 — транспорт и ошибки

WB adapter использует только необходимые фиксированные HTTPS-hosts; Authorization
отправляется только разрешённому WB host. Redirects запрещены явно, TLS verification
включена. Пользователь/LLM не выбирает URL, заголовки авторизации или base_url.
Таймауты, cancellation и лимит body обязательны. Проверять ID/path segments,
даты и объём выборок. Ошибки различают отсутствие конфигурации, denial,
authentication failure, rate limit, timeout, временную недоступность, неверный
ответ/контракт; не передают raw payload пользователю или LLM.

## WA-D132 — лимиты, пагинация и повторы

Лимиты привязаны к кабинету и группе endpoint согласно официальной документации.
Учитывать Retry-After, общий deadline и ограничение числа попыток.
Повторяемость определяется смыслом API, не HTTP method. Непроверенный write-path
повторять нельзя. Пагинация завершается по контракту endpoint, имеет ограничение
страниц/объёма и защиту от повторяющегося cursor. Каждый запрос учитывает общий
лимитер; достижение локального лимита означает partial, не success.

## WA-D133 — уникальность и сопоставления

Внешние записи уникальны в пределах provider/connection и внешнего ID.
Везде сохраняется workshop scope с проверкой согласованности connection.
Остатки различаются по connection + типу/ID склада + варианту/баркоду в терминах
выбранного endpoint, не только nmID. Точные ключи уточнить по JSON-контракту до DDL.
Mapping ссылается на product той же мастерской; неоднозначность остаётся
«не сопоставлено», а не разрешается по совпадению названия. Эти ограничения
проверяются и сервисом, и подходящими SQL constraints/queries.

## WA-D134 — полное и частичное обновление

SyncRun имеет состояния pending/running/succeeded/partial/failed/cancelled
(названия могут уточняться без изменения смысла). Полный успех отмечается только
после получения всех согласованных страниц/частей и успешной фиксации данных.
Отсутствие позиции в partial-выборке не означает удаление или ноль.
Успех одного типа загрузки не маскирует ошибку другого. Last full success
сохраняется при ошибке; UI показывает давность и неполноту отдельно.
Курсор продвигается вместе с локальным сохранением обработанной страницы.
Повтор страницы после сбоя допустим без дубликатов. Для снимков выбирать staging
или иной способ недопущения смешивания поколений данных до миграции.

## WA-D135 — транзакции и конкурентность

Сетевое ожидание не удерживает SQL-транзакцию. HTTP и локальная фиксация разделены.
Долгая загрузка не блокирует Telegram polling/другие диалоги. Повторная команда
не запускает конкурирующую загрузку того же scope/типа без координации.
Отключение/смена scope проверяются до следующего запроса и перед публикацией.

## WA-D136 — граница цеха

Импорт — обновление внешних сущностей L1. Производственные сервисы не вызываются
для автоматического выпуска, расхода, создания задач или отгрузки по факту
получения WB-заказа. Уникальность внешнего заказа не подменяет idempotency проводок.
Расширение этого поведения требует нового решения с явным пользовательским действием.

## WA-D137 — контекст модели

Внешние тексты не расширяют полномочия LLM. В модель передаётся только ограниченная
нужная выборка L1 с датой и признаком partial. История/long-term memory не заменяют
актуальную проверку доступа или запрос к локальным business records.
Отказ WB/пустая выборка/устаревшие данные имеют разные пользовательские ответы.

## WA-D138 — аудит

Записывать безопасные метаданные изменения подключения, mapping и загрузки:
кто, где, что, когда и результат. Не логировать целые DTO с credential.
Согласовать запись с существующим audit API: его текущий Log проверяет AuditRead;
не выдавать дополнительное право чтения аудита только ради технической записи.
Способ внутренней записи определить при реализации и покрыть тестом.

## WA-D139 — сверка API

Upstream audited commit — справочник форм запросов, не нормативная схема WB.
Для каждого выбранного метода перед реализацией сохранить host/path, method,
права, входы/выходы, лимиты, пагинацию, официальный URL и дату полной сверки.
Неподтверждённые параметры не объявлять актуальными.

### Детализация реализации WA-D128/133–135/138 (2026-09-22)

Одна строка подключения WB (ID=1) закрепляется за мастерской навсегда в первом
этапе. Повторное включение разрешено только там. Seller sid фиксируется после
проверки; иной sid блокирует загрузку без замены старых данных. При каждом новом
процессе идентичность проверяется заново до импорта.

Загрузки catalog, seller_stocks, wb_stocks, orders имеют независимые результаты.
Каждый тип собирает ограниченный снимок в памяти и публикует одной короткой
транзакцией; ошибка страницы сохраняет старый снимок целиком. Курсоры между
запусками не сохраняются: повтор начинается с начала. Это не массовая выгрузка.
Остаток уникален по connection/типу склада/warehouse_id/chrt_id; карточка — nmID,
вариант — chrtID; баркоды — отдельные строки варианта. Заказы сохраняются по ID,
статусы обновляются также для ранее импортированных заказов.

Проверка/синхронизация выполняются фоновой работой с общим deadline и mutex на
кабинет. Отключение отменяет context и увеличивает revision. Повторная авторизация
и revision проверяются перед HTTP и при публикации. Состояния прерванных при
перезапуске работ переводятся в cancelled без изменения снимков/last_success.
Технический аудит пишет фиксированные события в audit_logs внутри авторизованной
транзакции, не используя AuditRead как право записи и не расширяя его пользователю.
