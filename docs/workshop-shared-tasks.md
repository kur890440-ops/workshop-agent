# WORKSHOP_SHARED_TASKS

Обновление WA-D092: завершение теперь проводит выпуск и складские движения,
см. [TASK_COMPLETION_AND_MATERIAL_WRITEOFF](task-completion-posting.md).
Просмотр, назначение и создание задачи по-прежнему не меняют склад.

@PROJECT:WORKSHOP_AGENT @UPDATE @NO_COMPRESS

## L0 — Architecture

Рабочие задачи assembly и production принадлежат Workshop. Общий список,
авторство и исполнение разделены. Используются существующие working_memory,
pending_actions, FSM и Audit Log. История диалога, настройки и личная память
остаются персональными. Полноценной системы заказов по-прежнему нет.

## L1 — Model and migration

SQLite migration 105 добавляет created_by_user_id и assigned_to_user_id.
В существующих рабочих задачах оба поля заполняются прежним user_id. Сам user_id
сохраняет исторический смысл: переназначение его не меняет. Другие типы памяти
остаются персональными. ID, state_json, статусы, даты и история задач сохранены.
Неактивный Membership не удаляет историческую связь; карточка показывает необходимость
переназначения, а бывший участник теряет доступ через обычную авторизацию.

Уникальный индекс текущей задачи использует COALESCE(assigned_to_user_id,user_id)
и workshop_id. Для рабочих задач это исполнитель, для персональных — владелец.
active/waiting_input означают текущую задачу даже на этапе подготовки задачи; одна такая
задача на исполнителя сохранена. Несколько paused разрешены, выбор явный.
Старые пути создания совместимы через trigger заполнения автора и исполнителя.

## L2 — Decisions

- **WA-D086:** персональная видимость рабочих задач из WA-D076 и L1 ASSEMBLY_TASK_INTENT
  заменена общим списком Workshop. «Мои задачи» и текущая задача выбираются по исполнителю.
  История прежнего решения сохранена; личная память не становится общей.
- **WA-D087:** tasks.read доступно всем четырём ролям; tasks.create, tasks.assign,
  tasks.manage — OWNER/ADMIN; tasks.execute — OWNER/ADMIN/EMPLOYEE. EMPLOYEE не получает
  право создания: оно остаётся доступным только OWNER/ADMIN.
  Авторство само по себе не разрешает изменение чужой задачи.
- **WA-D088:** исполнитель — активный OWNER/ADMIN/EMPLOYEE той же Workshop. Есть
  «Назначить себе». Если единственный допустимый исполнитель — автор, он назначается
  автоматически и явно указан в подтверждении. Прямой /task new назначает автору;
  администратор затем может сменить исполнителя через карточку.
- **WA-D089:** создание и назначение проверяют права, Membership, Workshop и версию
  транзакционно. Изменение назначения, version, история и Audit Log атомарны.
  Аудит содержит фактического автора действия и прежнего/нового исполнителя.
- **WA-D090:** назначение не меняет ID, состав, этап или статус. Для execution/validation
  требуется явная пауза. Конфликт текущей задачи нового исполнителя блокирует назначение;
  UI предлагает другого исполнителя либо список задач. Автоматической паузы нет.
- **WA-D091:** общий Task DTO и контекст не раскрывают OpenQuestions и произвольные
  Parameters. Разрешены поля товара, количества, результата и рабочие ключи packaging,
  material, orders, per_order. Заметки, presentation overrides и неизвестные ключи
  остаются в БД; legacy-обновление сохраняет скрытые поля. История не выводит raw metadata.
- **WA-D092:** просмотр, назначение и FSM не меняют склад, BOM и production_records.
  Уведомления сотрудникам не отправляются. Они видят задачи в списке и «Мои задачи».

## L3 — Telegram and checks

`/orders`, «заказы», «текущие заказы», «покажи заказы», «список заказов», «задачи»,
«список задач» открывают общий список активной Workshop. Список имеет пагинацию,
устойчивые task_id, автора, исполнителя и состояние. Терминальные записи исключены.
Фильтр «Мои задачи» использует исполнителя. `/task` и «что в работе?» остаются
персональным входом исполнителя; доступ к общей задаче не открывает сессию её автора.

Уточнение UI: «пауза» без ID управляет текущей задачей отправителя, а не произвольной
строкой общего списка. Если личная задача не найдена, бот объясняет это и открывает
общий список, не предлагает создавать новую задачу. Для чужой задачи администратор
выбирает карточку → «Поставить на паузу» → подтверждение. Просмотр списка сам по себе
не выбирает задачу для изменения. Сценарий проверяется TestPauseWithoutAssignedTaskOffersSharedList.

OWNER: «собрать 5 дефлекторов» → товар → сотрудник → подтверждение с автором,
исполнителем и Workshop → «Создать задачу». Сотрудник открывает /task и выполняет FSM.
Другой EMPLOYEE может читать карточку, но не менять её. VIEWER только читает.
Переназначение: карточка → «Сменить исполнителя» → участник → подтверждение.
Исполнителя можно изменить и перед сохранением новой задачи.

Старые кнопки проверяют пользователя, чат, Workshop и версию. Прежний исполнитель
теряет право изменения после переназначения; если он администратор, остаются его
административные права, но устаревшая версия всё равно отклоняется.
Смена Workshop инвалидирует формы и кнопки прежнего меню.

Тесты: общий список и фильтр, создание для сотрудника, его /task, права ролей,
переназначение, устаревшая версия, конфликт, конкурентное назначение, удаление участника,
изоляция Workshop, скрытие приватных полей, сохранность state_json, actor истории,
миграция legacy и lifecycle-статусов. Используются временные БД и fake Telegram transport.

Проверка: `go test ./...`. Сборка: `go build -o bin/workshop-agent.exe ./cmd/workshop-agent`.
Миграция применяется автоматически при запуске обновлённого exe.
Для применения изменений: **Ctrl+C → `.\bin\workshop-agent.exe`**.
