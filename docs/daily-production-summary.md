# Daily Production Summary

@PROJECT:WORKSHOP_AGENT @L3:DAILY_PRODUCTION_SUMMARY @UPDATE @NO_COMPRESS

## L0 — Architecture

Telegram command/menu or semantic intent → Authorization → Products.DailyProduction
→ production_records + products in SQLite → deterministic rendering.
Сводка не создаёт заказы, задачи, производство, движения или таблицу агрегатов.
LLM распознаёт только свободное намерение; числа за сегодня считает сервис.
Ранее реализованные блоки материалов сохраняются. В свободных персонализированных
сводках и производственных отчётах дневной блок добавляется приложением после
генерации существующего отчёта, без LLM-переписывания чисел дневного блока.

## L1 — Sources and scope

- production_records — факты производства; good_quantity и scrap_quantity отдельно.
- products — актуальное название по product_id в той же Workshop. Продукты проекта
  учитываются в штуках; отдельного поля единицы для продуктов сейчас нет.
- Группировка по product_id. Совпадающие названия помечаются номером товара.
- Движения, складские остатки, планы, рабочие задачи и shipments не являются
  источником количества произведённой продукции или собранных заказов.
- Сущности заказов, их состава и события завершения сборки нет. Всегда выводится
  «Собрано заказов: учёт пока не настроен», а не выдуманный ноль.
- Настройки timezone Workshop нет; применяется Europe/Moscow. tzdata включена
  в бинарник для одинакового поведения на Windows без внешней базы часовых поясов.

## L2 — Decisions

- **WA-D066**: заказы и единицы продукции — разные показатели. До появления
  order_id, состава заказа, lifecycle и completed_at подсчёт заказов недоступен.
- **WA-D067**: период [начало местного дня, начало следующего местного дня).
  Используется production_records.date как дата производственного события,
  никогда created_at. RFC3339 учитывает offset; SQL timestamp без offset трактуется
  как UTC; историческая дата YYYY-MM-DD — календарный день мастерской.
- **WA-D068**: отсутствующая/невалидная дата не приписывается текущему дню.
  Такие записи дают предупреждение о неполном итоге. Нет нулевого утверждения
  «ничего не производилось», если имеются записи, которые невозможно датировать.
- **WA-D069**: только чтение production_records, без соединения с движениями,
  которое могло бы удвоить количество. Годные изделия и брак суммируются отдельно.
  Нет динамической дедупликации разных production_records с похожими данными:
  без ключа исходной операции невозможно отличить дубликат от реального выпуска.
- **WA-D070**: Membership, WorkshopRead, ProductionRead и ProductsRead проверяются
  внутри читающей транзакции. Материалы проверяют InventoryRead отдельно.
  Отсутствие права обозначается текстом, не нулём. Кнопка проверяет активную Workshop.

## L3 — UI, implementation, checks

Открыть: `/summary`, `/summary today`, «сводка», «сводка за сегодня»,
«сколько сегодня заказов собрано», «сколько сегодня сделали», «что сегодня произвели».
Регистр и пробелы по краям не влияют. В `/workshop` добавлена кнопка
«📊 Сводка за сегодня». Точные фразы обходят LLM. Свободная формулировка, например
«каковы итоги сегодняшнего выпуска?», классифицируется как get_daily_summary;
семантическая схема запрещает присылать количества, ссылки на материалы и единицы.
Неподдержанные периоды не должны превращаться в сегодняшний отчёт.

Текущий незавершённый пошаговый ввод имеет приоритет над обычными фразами;
для выхода используется `/setup_stop`. Длинные сообщения делятся существующим
UTF-16 splitter на части до 3500 единиц, все исходящие части учитываются обычным
Telegram-транспортом. Personalization не меняет расчёт и период; прежний блок
материалов сохраняет настройки оформления.

Проверены: пустой день; несколько записей одного товара; одноимённые товары;
отдельный брак; UTC/offset/date-only; включённая и исключённая границы суток;
невалидные даты без fallback на created_at; независимость от остатков/движений;
повторное чтение без удвоения; чужие пользователи/Workshop; локальные фразы,
семантический маршрут и кнопка; сохранение материалов; длинный текст с emoji.
Автотесты работают с временными БД и тестовым Telegram-транспортом.

Ограничения существующей модели: нет полноценного writer завершения производства
в Telegram (команды сборки/производства пока предлагают или планируют действия),
нет order lifecycle, нет status/cancelled_at/reversal_of у production_records.
Поэтому проверки завершённых/частичных/отменённых заказов и сторно не применимы
к текущей схеме. Отрицательные или повреждённые производственные значения
не трактуются самовольно как сторно: итог помечается неполным.
Новые lifecycle и idempotency производства не создавались в рамках этой задачи.
Реальные показатели появятся при наличии датированных фактов в production_records.

Верификация: `go test ./...` и сборка `bin/workshop-agent.exe`.
Рабочая БД не изменялась, реальные Telegram/LLM запросы для тестов не выполнялись.

Для применения изменений перезапусти бота:
**Ctrl+C → `.\bin\workshop-agent.exe`**.
