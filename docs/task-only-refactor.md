# TASK_ONLY — единая модель работы

## L0 — архитектура

Telegram / CLI → Identity + Active Workshop + Permissions → Task / TaskStateMachine
→ Invariants → Production / BOM / Inventory → SQLite.

Единственная сущность многошаговой работы — Task. Подготовка, выполнение,
проверка и завершение — этапы одной задачи. Отдельного модуля Plan больше нет.
LLM определяет намерение, но не записывает phase/status и не выполняет проводки.

## L1 — данные и ответственность

Источник состояния — `working_memory`: task_id, user_id, workshop_id, task_type,
state_json (task_data), phase, current_step, expected_action/type, status,
version, fsm_version, автор/исполнитель и timestamps.
История переходов — `task_transitions`, аудит — `audit_logs`.
Подтверждения содержат task_id/version и scope пользователя, чата, сессии,
мастерской. Working Memory использует тот же task_id.

Удалена неиспользуемая `models.ProductionPlan`. Прежняя
`products.ProductionPlan` переименована в `ProductionCalculation`: это значение
расчёта BOM/расхода и квитанция проводки, без собственного ID, lifecycle или
репозитория. Оно не является второй сущностью работы. Числа потребности
рассчитываются детерминированно по параметрам задачи и фактическому выпуску.

Отдельных PlanService, PlanRepository, PlanStateMachine и /plan-команд в исходном
коде не было. Не добавлены ни совместимые классы, ни aliases, ни второй callback
протокол. Существующие FSM / Memory / доменные сервисы сохранены.
Тип `production_plan` заменён на `production`, шаг `confirm_plan` — на
`confirm_task`; явное обновление старого формата — `adopt_task`.
Неиспользуемые planning.read/write удалены из политики; действуют tasks.*.

## L2 — решения и безопасная миграция

- **WA-D115:** только Task; техническая phase `planning` означает «Подготовка
  задачи». Нет создания новой сущности при подтверждении параметров.
- **WA-D116:** migration 108 переносит legacy `production_plans`, проверяет
  число задач и foreign keys, затем удаляет источник в той же транзакции.
  Перед миграцией существующего файла SQLite создаётся `.backup-<UTC>.db`
  через VACUUM INTO. Ошибка резервирования останавливает миграцию.
- **WA-D117:** уже существующие task_id, state_json, статусы, исполнители,
  даты, связи выпуска и история сохраняются. Меняются только старый task_type,
  идентификаторы шага/ожидания и категория памяти. Исторические события не
  переписываются. Pending completion подтверждения требуют нового предпросмотра:
  срок старых неподтверждённых intents сбрасывается; `plan_json` переименован
  в `calculation_json`. Проведённые результаты не отменяются.
- **WA-D118:** записи отдельной legacy-таблицы получают стабильный task_id
  из пары workshop_id + исходный ID. Все исходные колонки, включая описание,
  даты и дополнительные поля, сохраняются в parameters.legacy_source_record.
  Для записей без user_id/owner_user_id допустим ровно один активный OWNER;
  иначе миграция откатывается. Неизвестные внешние FK, включая CASCADE,
  блокируют удаление источника. Неизвестные статусы безопасно становятся paused,
  оригинал остаётся в metadata. completed/done не проводят выпуск повторно.
- **WA-D119:** новые FSM-события — TASK_CREATED, TASK_UPDATED, TASK_CONFIRMED,
  TASK_STARTED, TASK_PAUSED, TASK_RESUMED, TASK_VALIDATION_STARTED,
  TASK_COMPLETED, TASK_CANCELLED, TASK_FAILED. Состояние, переход и аудит
  фиксируются атомарно. Создание из черновика даёт одно TASK_CREATED.

В исходной схеме не было внешнего plan_id: ссылки производства и подтверждений
уже использовали task_id. Для отдельной исходной записи ID сохраняется в
архивных metadata; второй действующий идентификатор сущности не вводится.
Повторный запуск версии 108 не импортирует записи заново и не создаёт старую
таблицу. Остатки, BOM и production_records сама миграция не изменяет.

Существующие задачи fsm_version=0 остаются теми же Task. Явное управление
переводит их в FSM v1 с сохранением ID; просмотр не начинает выполнение.
Это совместимость формата Task, а не самостоятельная сущность Plan.

## L3 — интерфейс и проверка

- `/tasks`, «задачи», «Что сейчас в работе?» открывают общий список доступных
  задач мастерской. Кнопка «Задачи» есть в меню мастерской.
- `/task` открывает текущую задачу; `/task new` и
  «Создай задачу производства 25 дефлекторов.» создают одну Task в подготовке.
  Если товар неоднозначен, задача ожидает его явного выбора.
- Подготовка задачи → подтверждение количества/параметров → выполнение →
  ввод фактического результата → проверка → «Завершить и списать» → завершено.
  Весь путь использует один task_id. Пауза и продолжение сохраняют этап и данные.
- Подтверждение параметров не списывает склад. Только подтверждённое завершение
  атомарно проводит выпуск, расход компонентов и TASK_COMPLETED.
- Старые кнопки процесса после перезапуска недействительны; карточку нужно
  открыть заново. Существующие /orders и текстовые aliases заказов показывают
  задачи с честным пояснением об отсутствии отдельного учёта заказов.
