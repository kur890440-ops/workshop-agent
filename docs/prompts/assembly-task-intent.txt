Добавить понятный вход в просмотр текущих заказов/задач и создание задачи сборки через обычные сообщения пользователя.

Сейчас на слово «заказ» бот предлагает уточнить материал и складское действие.
Исправить маршрутизацию: просмотр заказов ведёт к списку существующих записей; создание новой сборки — к выбору товара и подтверждению новой задачи в существующей Task State Machine.

Переиспользовать Working Memory, FSM Day 13, каталог Products, BOM,
существующий Telegram UI и семантический обработчик.
Не создавать параллельную систему задач или черновиков.

1. РАСПОЗНАВАНИЕ НАМЕРЕНИЯ

Поддержать:
- заказ;
- собрать заказ;
- новый заказ;
- нужно собрать заказ;
- собрать дефлектор;
- собрать 5 дефлекторов;
- сделаем 5 сливов;
- нужно собрать 3 набора.

Игнорировать регистр и пробелы по краям.
Учитывать словоформы, сокращённые названия и контекст текущего диалога.

Точные фразы обрабатывать локально без LLM.
Свободные формулировки — через существующий семантический обработчик.
Локальный и семантический маршруты одного намерения должны вызывать один сценарий. Просмотр существующих записей и создание новой задачи — разные намерения.

Не использовать простое вхождение слова «заказ»:
- «что нужно заказать?» — закупки;
- «сколько заказов собрано сегодня?» — сводка;
- «какой остаток дефлекторов?» — просмотр остатков;
- «не создавай заказ» — не создавать задачу.

Не направлять запрос о сборке в уточнение материала или изменение остатков.

2. ПРЕДЛОЖЕНИЕ СОЗДАТЬ ЗАДАЧУ

На «новая задача сборки» или явное создание новой сборки ответить. Для «заказ», «заказы» и «собрать заказ» применять раздел 10, без автоматического создания:

«Создать задачу сборки?
Выберите товар, который нужно собрать.»

Показать товары текущей Workshop пронумерованным списком
и кнопками выбора, используя существующее меню товаров.

До окончательного подтверждения пользователя задача не создаётся.
На этом этапе сохраняется только черновик намерения.

Если товаров нет:
«В мастерской пока нет товаров. Сначала добавьте товар.»

Предложить существующий сценарий добавления товара только при наличии прав.

3. ПОДБОР ПОДХОДЯЩИХ ТОВАРОВ

На «собрать дефлектор» найти товары, соответствующие названию.

Например:
1. Дефлектор Ballu — белый.
2. Дефлектор Ballu — чёрный.
3. Дефлектор Electrolux.

Не выбирать случайный вариант при нескольких совпадениях.
Предложить пользователю выбрать конкретный товар.

Если найден один товар:
«Подойдёт “Дефлектор Ballu — белый”?»
Кнопки: «Выбрать», «Другой товар», «Отмена».

Если совпадений нет:
«Подходящий товар не найден. Выберите из каталога.»
Показать доступные товары текущей Workshop.

Совпадение названия не является основанием автоматически создавать товар.
LLM может помогать понимать название, но существование товара и его
принадлежность Workshop проверяются сервером.

Номер и кнопка должны ссылаться на устойчивый product_id.
Не путать ID товара с позицией в показанном списке.

4. КОЛИЧЕСТВО

После выбора товара запросить количество, если пользователь его не указал:

«Сколько единиц “Дефлектор Ballu — белый” нужно собрать?»

Если пользователь написал «собрать 5 дефлекторов»:
- сохранить количество 5 в черновике;
- после выбора конкретного товара не запрашивать его повторно;
- показать количество при подтверждении.

Поддержать исправление:
«Нет, 10» → изменить количество в том же черновике.

Для штучной продукции принимать только положительные целые числа
в пределах существующих ограничений проекта.
Отклонять ноль, отрицательные, дробные, NaN и бесконечность.

Заказ и единица товара — разные понятия:
«5 заказов» не означает «5 изделий».
Если указано количество заказов, уточнить товар и число единиц в каждом,
показать вычисленный итог для подтверждения.
Не заявлять о создании полноценного заказа, если такой сущности в проекте нет.

5. ПОДТВЕРЖДЕНИЕ

Показать:

«Создать задачу сборки?

Товар: Дефлектор Ballu — белый.
Количество: 5 шт.
Мастерская: {название}.»

Если BOM задан, можно добавить рассчитанный состав и потребность
через существующий доменный сервис.

Если BOM отсутствует, явно сообщить:
«Состав товара пока не задан. Расход материалов рассчитать нельзя.»

Отсутствие BOM не должно приводить к выдуманному расходу
или сообщению о готовности к фактическому производству.

Кнопки:
- «Создать задачу»;
- «Изменить товар»;
- «Изменить количество»;
- «Отмена».

6. СОЗДАНИЕ ЗАДАЧИ

После подтверждения создать ровно одну задачу нового FSM-формата
в существующей working_memory.

Использовать поддержанный тип задачи: сборка или производство.
Если нужно расширить существующий FSM, сделать это явно;
не создавать ещё один несовместимый legacy-сценарий.

Сохранить:
- task_id;
- user_id;
- workshop_id;
- product_id;
- количество;
- phase=planning;
- status=active;
- корректные current_step и expected_action.

Шаг после создания должен соответствовать уже подтверждённым данным.
Не заставлять пользователя заново выбирать товар и вводить количество.

Подтверждение создания задачи не означает подтверждение начала производства.
Не переводить задачу автоматически в execution.

После создания показать карточку задачи:
товар, количество, этап, шаг, ожидаемое действие,
кнопки паузы, отмены и допустимого следующего действия.

Созданная задача должна поддерживать:
- /task;
- «что в работе?»;
- «сделай паузу»;
- «продолжим»;
- новую сессию;
- перезапуск приложения.

7. ЕСЛИ ЗАДАЧА УЖЕ ЕСТЬ

Не перезаписывать текущую задачу и не закрывать её автоматически.

Сообщить:
«У вас уже есть активная задача: {краткое описание}.»

Предложить:
- «Открыть текущую»;
- «Поставить текущую на паузу и продолжить создание»;
- «Отмена».

Пауза существующей задачи требует явного выбора пользователя.
Её данные и шаг должны сохраниться.

Соблюдать правило одной активной задачи на user + workshop.
Несколько paused-задач не являются поводом выбирать одну автоматически.

8. СОХРАННОСТЬ И БЕЗОПАСНОСТЬ

- Проверять Membership, текущую Workshop и соответствующие Permissions.
- Показывать товары только текущей Workshop.
- Повторно проверять права и product_id при подтверждении.
- При смене Workshop инвалидировать старые кнопки и черновик выбора.
- Не принимать номер из чужого, устаревшего или другого каталога.
- Защитить подтверждение от повторного нажатия и конкурентного создания:
  потребление черновика и создание задачи должны быть атомарными.
- /setup_stop и «Отмена» отменяют черновик без создания задачи.
- После рестарта устаревшая кнопка не должна создавать задачу.
- Создание задачи не меняет остатки, BOM и production_records.
- Personalization меняет только оформление, не проверки и переходы.
- Не хранить черновик только в тексте истории разговора.
- Для длинных каталогов использовать разбиение или пагинацию
  с корректной привязкой номеров к товарам.

9. ПРОВЕРКИ

Проверить:
- «заказ», «заказы» и «собрать заказ» открывают список текущих записей без создания задачи;
- «новая задача сборки» открывает предложение выбрать товар;
- «собрать дефлектор» предлагает подходящие варианты;
- один, несколько и отсутствие совпадений;
- словоформы: дефлектор/дефлекторов, слив/сливов;
- количество из исходной фразы сохраняется;
- изменение товара и количества;
- различие числа заказов и числа изделий;
- отсутствие товаров и отсутствие BOM;
- до подтверждения задачи нет;
- подтверждение создаёт одну FSM-задачу;
- повторное нажатие не создаёт дубликат;
- текущая задача не перезаписывается;
- пауза текущей задачи только по явному выбору;
- отмена и /setup_stop;
- смена Workshop, устаревшие кнопки, отсутствие прав;
- пауза и продолжение созданной задачи после новой сессии и рестарта;
- запросы закупок, остатков и дневной сводки сохраняют свои маршруты;
- доменные данные не изменяются.

10. УТОЧНЕНИЕ: СПИСОК ТЕКУЩИХ ЗАКАЗОВ И ПЕРЕХОД К СБОРКЕ

Разделить просмотр текущих заказов и создание новой задачи.
Этот раздел заменяет прежнее правило, направлявшее любое слово «заказ»
в создание задачи. Разделы 2–7 относятся к созданию новой сборки,
а не к просмотру или продолжению уже существующей записи.

10.1. ПРОСМОТР

Фразы:
- заказ;
- заказы;
- текущие заказы;
- покажи заказы;
- список заказов

открывают список текущих незавершённых заказов текущей Workshop.
Не запускать создание новой задачи на эти фразы.

Пример:

«Текущие заказы:
1. Заказ №123 — 5 дефлекторов Ballu. Ожидает сборки.
2. Заказ №124 — 3 слива Advantix. Сборка на паузе.

Выберите заказ, чтобы открыть состав и перейти к сборке.»

Под списком:
- кнопки выбора заказов;
- «Новый заказ» — только если создание заказов уже поддержано.

Номер в списке связывать с устойчивым order_id, а не использовать
как ID записи. Для длинного списка предусмотреть пагинацию.

10.2. ВЫБОР И СБОРКА

После выбора показать:
- номер заказа;
- товары и количество каждого;
- текущий статус;
- связанную задачу сборки, если она есть.

Предложить подходящее действие:
- «Собрать заказ» — если сборка ещё не начата;
- «Продолжить сборку» — если связанная задача на паузе;
- «Открыть задачу» — если сборка уже выполняется;
- «Назад к заказам».

Не начинать сборку и не менять статус только из-за просмотра списка
или выбора заказа.

«Собрать заказ» открывает подтверждение создания задачи сборки
из состава выбранного заказа. Повторно выбирать известные товары
и вводить их количество не нужно.

Если заказ содержит несколько позиций, сохранить весь состав.
Не заменять его одним товаром.

Если задача сборки уже существует, использовать её:
не создавать дубликат.

Возобновление и начало выполнения проводить через существующий FSM
с проверкой допустимого перехода и подтверждения пользователя.

10.3. СОЗДАНИЕ НОВОГО

Фразы «новый заказ», «создать заказ» явно выражают намерение создать
новый заказ и не должны смешиваться с просмотром списка.

«Собрать заказ» или «нужно собрать заказ» без номера или выбранного заказа:
показать текущие заказы и предложить выбрать нужный.
При наличии номера или выбранной записи открыть её карточку,
проверив доступ и актуальность состояния.

«Собрать 5 дефлекторов» без ссылки на существующий заказ:
предложить создание задачи сборки по исходному сценарию
выбора товара, количества и подтверждения.

10.4. ЕСЛИ ПОЛНОЦЕННОГО УЧЁТА ЗАКАЗОВ ПОКА НЕТ

Не выдавать рабочие задачи за настоящие заказы.

Команда «заказы» должна показать существующие незавершённые задачи
сборки и производственные задачи с честным заголовком:

«Учёт заказов пока не настроен.
Текущие задачи сборки:
1. Слив боковой Advantix — 5 шт. Подготовка задачи.
2. Дефлектор Ballu — 10 шт. На паузе.»

В этом режиме:
- позиции связывать с task_id;
- показывать active и paused задачи соответствующих типов;
- не включать завершённые, отменённые и failed задачи;
- после выбора предлагать допустимое действие текущего FSM:
  подтвердить задачу, начать выполнение, продолжить или открыть задачу;
- не создавать новую задачу для уже выбранной задачи;
- использовать кнопку «Новая задача сборки», а не «Новый заказ».

Если список пуст:
«Текущих задач сборки нет.»
Кнопка: «Новая задача сборки».

На «новый заказ» или «создать заказ» в этом режиме объяснить,
что доступно создание задачи сборки, и предложить этот сценарий.
Не утверждать, что создан полноценный заказ.

Не создавать отдельную систему заказов в рамках этой задачи.

10.5. ДОСТУП И ПРОВЕРКИ

- Сохранять текущую модель доступа: персональные задачи доступны
  их владельцу, заказы — по существующим правам проекта.
- Не раскрывать чужие задачи только потому, что Workshop общая.
- Повторно проверять права, текущую Workshop и состояние записи
  при выборе и подтверждении действия.
- Старые кнопки не должны запускать сборку другого заказа
  или задачи после смены Workshop.
- При наличии другой активной задачи предлагать её открыть
  либо явно поставить на паузу; не переключать автоматически.
- Просмотр списка не меняет задачи, остатки и production_records.
- Если выбранная задача уже активна, открывать её без создания дубликата.
- Существующие незавершённые legacy-задачи не терять из списка из-за
  старого формата; использовать имеющуюся совместимость.
- Перевод legacy-задачи в FSM выполнять только при явном управлении,
  сохраняя task_id и параметры, а не при просмотре.

Дополнить тесты:
- «заказы» выводит список, не создавая задачу;
- пустой список;
- несколько заказов или задач;
- корректный состав многопозиционного заказа, если он поддерживается;
- выбор по устойчивому ID;
- начало и продолжение сборки через FSM;
- отсутствие дубликата связанной задачи;
- исключение завершённых и отменённых записей;
- изоляция пользователей и Workshop;
- честный режим списка задач при отсутствии сущности заказа;
- отображение и продолжение legacy-задачи без дубликата.

Остальные требования исходного промпта сохранить:
тесты, документацию L0–L3, сборку и обязательное сообщение
о перезапуске бота.

Использовать тестовую БД и тестовый Telegram-транспорт.
Не создавать задачи и не отправлять сообщения в рабочий чат при автотестах.

Обновить документацию L0–L3 без сжатия предыдущих решений.
Запустить go test ./... и собрать bin/workshop-agent.exe.

В итоговом ответе показать короткий пример диалога,
описать ограничения и результаты проверок.

Обязательно написать:
«Для применения изменений перезапусти бота:
Ctrl+C → .\bin\workshop-agent.exe».
