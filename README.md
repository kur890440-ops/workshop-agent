# WorkshopAgent

WorkshopAgent — это AI-ассистент на Go для небольшого производственного цеха. Он использует Telegram как клиентский слой, отдельный сервис домена WorkshopAgent для интерпретации намерений пользователя и SQLite для всех реальных данных по складу, спецификациям BOM, производству и отгрузкам.

## Архитектура L0 — WORKSHOP_AGENT

Целевая архитектура проекта. Схема задаёт границы и порядок обработки; текущий MVP реализует её частично.

```text
TELEGRAM USER
↓
IDENTITY
↓
WORKSHOP CONTEXT
↓
MEMBERSHIP / ROLES / PERMISSIONS
↓
AUTHORIZATION
↓
TELEGRAM INTERFACE
↓

↓

├── Inventory
├── Materials
├── Components
├── Packaging
├── Products
├── BOM
├── Production
├── Scrap / Defects
├── Shipments
└── Planning
↓
DETERMINISTIC BUSINESS LOGIC
↓
SQLITE
```

## Архитектура L1 — IDENTITY_ACCESS

Детализация целевой архитектуры L0 для идентификации пользователей и доступа к Workshop.

### ENTITIES

- User
- Workshop
- WorkshopMembership
- WorkshopInvite
- Role
- Permission
- UserWorkshopContext
- AuditLog

### RELATION

```text
User
  ↓ many-to-many
WorkshopMembership
  ↓
Workshop
```

Связь User ↔ Workshop — many-to-many через WorkshopMembership: один пользователь может участвовать в нескольких Workshop, а один Workshop может иметь нескольких пользователей.

Пользователь не принадлежит другому пользователю.
Пользователь является самостоятельной сущностью
и получает доступ к Workshop через Membership.

## Решения L2 — IDENTITY_ACCESS

Принятые архитектурные решения для целевой архитектуры L0/L1.

### WA-D009

Одна Workshop может иметь нескольких Users.

### WA-D010

Один User может состоять в нескольких Workshops.

### WA-D011

Связь User ↔ Workshop хранится через WorkshopMembership.

### WA-D012

Telegram user_id является внешним идентификатором пользователя,
но не заменяет внутренний user_id.

### WA-D013

Добавление сотрудника производится через invite,
а не через Telegram username.

### WA-D014

Invite связывает нового/существующего User
с конкретной Workshop и Role.

### WA-D015

Удаление сотрудника удаляет Membership,
но не удаляет самого User.

### WA-D016

Domain data всегда имеет workshop scope.

### WA-D017

Любая операция с Inventory/BOM/Production/etc.
проверяет доступ к текущей Workshop.

### WA-D018

Роли первого этапа:

- OWNER
- ADMIN
- EMPLOYEE
- VIEWER.

### WA-D019

Permissions существуют отдельно от Role,
даже если сначала Role → Permissions задаются кодом.

### WA-D020

OWNER имеет особые права:
ownership нельзя случайно удалить;
передача ownership выполняется явно.

### WA-D021

Invite ограничен по времени,
может быть отозван
и по умолчанию одноразовый.

### WA-D022

Raw invite token не хранится в БД открытым текстом,
если архитектура позволяет хранить hash.

### WA-D023

Все изменения участников, ролей и приглашений
попадают в Audit Log.

### WA-D024

Пользователь имеет active_workshop context.

### WA-D025

Личные настройки принадлежат User,
а склад/BOM/production принадлежат Workshop.

### WA-D026

Будущая память:

- personal long-term → user scope;
- workshop knowledge → workshop scope;
- working memory → user + workshop + task;
- short-term → user + workshop + session.

## Основные принципы

В карточке товара кнопка «Состав товара» позволяет выбрать конкретные материалы,
коробки и пакеты с количеством на один товар. Изменения требуют подтверждения,
склад не меняется. [Состав товара, L0–L3](docs/product-composition-menu.md).

В меню товаров доступно «Редактировать продукт»: название, SKU, тип,
остаток и минимум, с подтверждением и защитой от устаревших данных.
[Редактор продуктов, L0–L3](docs/products-edit-menu.md).

«Товары» и `/products` открывают пронумерованный список без LLM.
Сценарий «соберём 5 заказов → товары → 2 → 3» сохраняет черновик и предлагает
план на 15 изделий; склад не меняется. [Продукты и контекст сборки, L0–L3](docs/products-assembly.md).

Контекстная семантика: после списка материалов можно спросить «какой остаток 2», «а кисточек сколько?» или «а его минимум?». Свободные изменения требуют подтверждения. [Архитектура L0–L3, проверки и результаты реальной модели](docs/semantic-processing.md).

Очистка личного чата: `/clear` или «очисти» → подтверждение. [Сценарий, ограничения Telegram и решения L0–L3](docs/chat-clear.md). Удаляются известные доступные сообщения; задачи и данные мастерской сохраняются.

Меню материалов реализовано. [Фиксация L0–L3, решения WA-D027–WA-D033, сценарии и проверки](docs/materials-menu.md).

Рабочие единицы материалов реализованы: [L0–L3, решения WA-D034–WA-D037](docs/material-display-units.md). Для гипса в кг: `/materials` → «Единица измерения» → номер гипса → «кг» → «Подтвердить». Хранение остаётся в граммах, ввод и вывод — в кг.

Day 11 Memory Layers реализован. [Архитектура, команды и ограничения](docs/day11-memory.md) · [HTML-отчёт эксперимента](reports/day11-memory/20260916T174744.744562000Z/report.html).

- LLM используется только для разбора естественного языка и создания структурированных действий.
- SQLite является источником истины для всех данных по складу, BOM, остаткам и движениям.
- Бизнес-правила реализованы в Go и хранятся в SQLite.
- Данные для нескольких арендаторов изолированы по workshop_id.
- Для операций записи используется явное подтверждение. Исключение для меню материалов (WA-D029): число без знака устанавливает остаток, число с начальным + или - меняет его относительно текущего; корректный ввод сразу сохраняется; создание материала сохраняет подтверждение «да».

## Статус проекта

Этот репозиторий является базой MVP для запрошенной архитектуры. В него входят Go-модуль, слой данных на SQLite, модель workshops/users, логика материалов и продуктов, рекурсивный расчёт BOM и поток WorkshopAgent на базе MockLLM.

Этап Identity & Access реализован: независимые пользователи и мастерские, Memberships, приглашения, роли/permissions, активная мастерская, авторизация внутри сервисов и Telegram UI управления сотрудниками. Следующими отдельными заданиями реализованы Day 11 Memory Layers, [Day 12 Personalization](docs/day12-personalization.md) и [Day 13 Task State Machine](docs/day13-task-state.md). ### Day 13 — состояние задачи

`/task new` создаёт производственный план с этапами planning → execution → validation → done.
`/task pause` сохраняет текущий шаг, `/task resume` продолжает его после новой сессии
или перезапуска, `/task trace` показывает диагностику. В `/workshop` есть кнопка
«📋 Текущая задача». Старые планы сохраняют прежний сценарий.

## Запуск

1. Скопируйте `.env.example` в `.env` и заполните секреты.
2. Запустите:
   - `go mod tidy`
   - `go test ./...`
    - `go run ./cmd/workshop-agent setup` — создать и проверить все таблицы SQLite.
    - `go run ./cmd/workshop-agent` — запустить Telegram-бота.

Команда `setup` безопасна для повторного запуска: она не удаляет существующие данные.

### Настройка через Telegram

После запуска бота отправьте в чат:

- `/setup` — создать/проверить таблицы и показать текущие материалы и продукты.
- `/materials` — пронумерованный список материалов; «Добавить» открывает форму, «Редактировать» запрашивает номер и новый остаток (`10000`, `0`) либо изменение со знаком (`+5`, `-2,5`). После сохранения меню обновляется. Доступность действий зависит от permissions. Слова «материалы» и «остатки» вне формы ввода открывают это же меню без LLM; регистр не важен.
- `/setup_add_material` — пошагово добавить материал с выбором категории и единицы измерения.
- `/setup_add_product` — пошагово добавить продукт с выбором типа.
- `/to_order` — показать материалы, достигшие минимального остатка, и рекомендуемое количество к заказу.
- `/setup_stop` — остановить режим настройки без удаления данных.
- `/start` — регистрация пользователя и открытие текущей мастерской; при отсутствии мастерских — предложение создать свою.
- `/workshop` — текущая мастерская, сотрудники, приглашения и управление доступом.
- `/workshops` — выбор активной мастерской.
- `/members` — список сотрудников текущей мастерской.
- `/task`, «задачи» или «задача» — показать текущую активную задачу пользователя в выбранной мастерской без обращения к LLM. Слова без слеша действуют вне формы ввода; регистр не важен.

Работа с данными и управление доступны в личном чате с ботом. Добавление сотрудника: `/workshop` → **Пригласить** → роль → подтверждение → ссылка. Получатель ссылки сам подтверждает присоединение. Кнопки управления отображаются по permissions; права повторно проверяются при выполнении действия.

Существующие пользователи, данные и мастерские сохраняются при миграции. Перед первым обновлением старой SQLite создаётся файл `data/workshop.db.backup-<timestamp>.db`. Автоматическое создание demo-мастерских при запуске отключено.

Для остановки самого бота используйте `Ctrl+C` в окне PowerShell.

### Свободные вопросы в Telegram

Обычный текст без слеша обрабатывается через настроенную LLM. Например:

- `Сколько сейчас гипса на складе?`
- `Что нужно заказать?`
- `Какие материалы заканчиваются?`
- `Сколько товара Stitch осталось?`

LLM определяет намерение и извлекает название материала или продукта, а остатки и закупка рассчитываются Go по данным SQLite. Команды `/materials`, `/stock` и `/to_order` работают напрямую и не используют LLM.

После свободного вопроса бот также показывает расход LLM-токенов: входные токены, токены ответа и общий расход. Эти значения берутся из поля `usage` ответа OpenRouter. Для локальных команд и локально распознанных вопросов отображается `Токены LLM: 0 (локальная обработка)`.

## Переменные окружения

- `TELEGRAM_BOT_TOKEN` — токен Telegram-бота.
- `LLM_API_KEY` — API-ключ для совместимого с OpenAI endpoint.
- `LLM_BASE_URL` — базовый URL провайдера LLM.
- `LLM_MODEL` — имя модели.
- `DATABASE_PATH` — путь к локальной базе SQLite внутри проекта; по умолчанию используется `./data/workshop.db`.
- `INVITE_TTL` — срок приглашения в формате Go duration, по умолчанию `24h`.
- `INVITE_MAX_USES` — число использований приглашения, по умолчанию `1`.
- `SHORT_TERM_MAX_MESSAGES` — максимум сообщений текущего диалога, по умолчанию `20`.
- `SHORT_TERM_MAX_TOKENS` — оценочный бюджет краткосрочной памяти, по умолчанию `1600`.

> База данных хранится локально в проекте: по умолчанию используется `./data/workshop.db`. Не указывайте системные/внешние пути, если хотите держать данные в репозитории и локально на машине.

## Заметки

### Завершение задачи и списание

Откройте задачу и начните выполнение через FSM. Напишите «готово 3» или
«завершить задачу» → введите фактический выпуск → проверьте состав и остатки →
**«Завершить и списать»**. Компоненты списываются по факту, готовый товар приходуется,
задача завершается и появляется запись производства. Всё проводится одной транзакцией.
Отмена: `/setup_stop`. Недостаток материалов блокирует всю операцию.
Повторное подтверждение не списывает повторно. Старые завершённые задачи автоматически
не проводятся. Для повторного просмотра результата: `/task complete <task_id>`.

[Архитектура, политика вложенного BOM и ограничения](docs/task-completion-posting.md).

### Заказы и задачи сборки

`/orders`, «заказы», «текущие заказы», «покажи заказы», «список заказов» и
«собрать заказ», «задачи» и «список задач» открывают общий список незавершённых задач текущей мастерской.
Полноценный учёт заказов пока не настроен — бот сообщает об этом в заголовке.
Выберите задачу, затем подтвердите доступное действие. Просмотр не начинает сборку.

Для новой сборки: «собрать 5 дефлекторов» → выбор товара → исполнитель → «Создать задачу».
Можно изменить товар и количество; «Нет, 10» исправляет количество в подтверждении.
Фильтры: «Все задачи» и «Мои задачи» (по исполнителю). OWNER/ADMIN назначают и
переназначают задачи; EMPLOYEE выполняет назначенные ему; VIEWER только читает.
В карточке есть «Сменить исполнителя» для администраторов. Выполняемую задачу сначала
нужно явно поставить на паузу. При конфликте автоматического переключения нет.
Склад при создании и назначении не меняется. Личные настройки и память не раскрываются.
Отмена черновика: `/setup_stop`.
